# ADR-0001: نحوهٔ تضمین جداسازی چندمستأجری

- **وضعیت:** پذیرفته‌شده
- **مرتبط با:** بخش ۴ سند معماری، فاز ۱

## زمینه

سند معماری می‌گوید `ITenantScopedRepository<T>` باید «هیچ Queryای بدون `tenantId` قبول نکند —
قفل کامپایل‌تایم/ران‌تایم». در C# نمی‌توان به‌طور کامل در زمان کامپایل تضمین کرد که یک فیلتر
دلخواه شامل `tenantId` باشد؛ پس باید ترکیبی از سازوکارها استفاده شود.

## تصمیم

دفاع چهارلایه:

1. **قید تایپ:** `where T : class, ITenantOwned` — موجودیتی که فیلد `TenantId` ندارد اصلاً
   نمی‌تواند از این ریپازیتوری عبور کند. خطای کامپایل.
2. **حذف پارامتر `tenantId` از امضای متدها:** مستأجر از `ITenantContext` تزریق‌شده در سازنده
   می‌آید. چیزی که پارامتر نیست، فراموش هم نمی‌شود و از ورودی کاربر هم نمی‌آید.
3. **تنها نقطهٔ ساخت فیلتر:** متد `ScopedFilter` تنها راه ساخت `FilterDefinition` است و همیشه
   `tenantId` را با AND اضافه می‌کند. هیچ API عمومی‌ای برای اجرای فیلتر خام وجود ندارد.
4. **تأیید هنگام نوشتن:** `EnsureBelongsToCurrentTenant` قبل از هر Insert/Replace بررسی می‌کند
   سند متعلق به مستأجر جاری باشد، وگرنه `CrossTenantAccessException`.

علاوه بر این، **تست‌های تضمینی** در `TenantIsolationTests` هر مسیر (خواندن با شناسه، لیست،
شمارش، فیلتر باز `_ => true`، حذف، جایگزینی) را با مستأجر دیگر می‌آزمایند و انتظار صفر نتیجه
دارند. این تست‌ها جزو فاز ۱ هستند، نه فاز ۱۲.

## پیامدها

- Collectionهای سطح پلتفرم (`platform_*`) عمداً از این مسیر عبور نمی‌کنند و باید ریپازیتوری
  جدا داشته باشند؛ فهرست‌شان در `MongoCollections.PlatformLevel` صریح است.
- `TenantContext` پس از یک بار ست‌شدن قابل تغییر نیست تا در میانهٔ یک درخواست عوض نشود.
- هر ایندکس MongoDB باید `tenantId` را به‌عنوان اولین کلید داشته باشد، وگرنه کوئری‌ها
  Collection Scan می‌شوند.
